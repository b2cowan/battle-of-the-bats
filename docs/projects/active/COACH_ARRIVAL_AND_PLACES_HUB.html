What each marker proposes

1

Arrival asks “how long before”, as a dropdown restyled

A coach thinks “be there 45 minutes early”, not “5:15”. The stored value stays the clock time families already see (“Arrive by 5:15 p.m.”), so nothing downstream changes — the calendar export, the game-day header, the event page. The control derives its state: if the arrival is exactly 45 minutes before the start, it reads “45 minutes before”.

The pushback on pills: a one-value form field is a dropdown here (your 08-22 convention), and it happens to be the better shape for this one — four pills hold four answers and the fifth still needs the clock; the list holds seven and the escape without crowding the row.

2

The list shows the clock beside each answer new

“45 minutes before · 5:15 p.m.” — the coach sees what families will read before choosing. Change the start time later and an arrival that was a preset follows it (the same “follows unless you set your own” rule the end time already has); a specific time stays put.

3

“A specific time…” opens an hour before the game new

This is the literal fix for the screenshot: the clock picker opened at the time of day you were sitting at (9:05 a.m.). Choosing a specific time now starts the clock at start − 1 hour, so the picker opens in the right neighbourhood and one tap adjusts it.

4

Defaulting every new game to “1 hour before” — a team setting, not a hard rule accepted

A hard default puts a promise on every family’s calendar the coach never made (“Arrive by 5:00” on a game where the coach meant nothing by it). A team’s habit is real, though, and it should be set once: Team Settings → Game day → Arrive before a game / a practice. New games start with it; any game can change it. Blank until the team says otherwise.

Recommendation: ship the dropdown now, and the team default with it — it is one row in Settings and it is what makes “1 hour before” the resting state for the teams that want it, without deciding for the ones that don’t.

5

A place is a thing the team keeps — name, address, usual diamond, a note new

Today a location is three loose strings on each event, and the Recent chips carry whatever address the most recent event with that name happened to have — usually nothing — and never the diamond. A place book fixes the cause: pick “Sherwood Park” and its address and Diamond 2 come with it. The picker is the tag picker’s grammar (type to find, add inline, a Manage door inside), so nothing new to learn.

Not a modal-first button: a button that opens a chooser is one more door before the field. Typing into the field is the door.

6

Find it, add it, or just type it new

The list shows the team’s places, most recently used first, with how many events sit at each. Typing a name that isn’t there offers ＋ Add “…” as a place (the small sheet at 7). And a coach who just wants to type “Kanata Rec Centre” for a one-off away game still can — a free-typed location saves as text exactly as today, with no place created. Manage places… is the last row, where minting lives.

7

Adding a place asks four things, three optional new

Name, address (the map link), the usual field or diamond, and a note that shows on the event (“park behind the arena”). Only the name is required, so adding a place is never slower than typing a location was.

8

The book opens already filled accepted

On first use, a team’s places are seeded from its own history — every distinct location it has ever used, with the best address and the most common diamond it recorded. Editing a place’s address asks whether to update the upcoming events at that place; past events keep what they had. Removing a place leaves its events’ text alone (they were always a copy).

The call: seed from history (recommended — the book is never empty for a team that has a season behind it) or start empty and let the Recent list do the seeding one pick at a time.

9

The diamond stays per-game; the address leaves More restyled

A park has six diamonds and a tournament puts you on a different one each game, so Field / Diamond # stays under More, pre-filled from the place and changeable for this game only (the hint says so). Address comes out of More: a place carries it, a mirrored tournament game shows the organizer’s, and a free-typed location gets one by saving the place — three fields for one street address was the noise the form just shed.

PM Brief — Arrival & Places (proposed)

Ruled 2026-09-21 (D1–D9 as drawn) · built on dev the same day

What a coach sees differently

  • Arrival on a game or practice is a dropdown of “how long before” — 15 minutes to 2 hours, with the clock shown beside each — and “A specific time…” for anything else, opening an hour before the game rather than at the time of day you happen to be sitting at. Families see exactly what they see today: “Arrive by 5:15 p.m.”
  • Team Settings gains “Arrive before a game / a practice” — set once, and every new event starts there. Blank until the team says otherwise.
  • Location becomes a place the team keeps. Type to find one of your places or add one inline (name, address, usual diamond, a note); picking it fills the address and diamond. A free-typed one-off location still works exactly as today. Recent chips retire into the picker’s list; Manage places lives inside it.
  • Under More, the diamond stays changeable per game (pre-filled from the place); the Address field goes — the place carries it.

Why it matters

Arrival and location are the two things a coach types on every game, and both were asking the question the wrong way round: a clock instead of a lead time, and three loose strings instead of the place the team actually goes to. The map link — the reason the address exists — only worked when a coach retyped the address, which is why it mostly didn’t.

What it touches

  • The event form (both changes), Team Settings (one row), the event page and game-day header (unchanged — same stored values), the schedule import (a row whose location matches a place takes its address), help articles for the schedule and game-day details.
  • Data: a per-team place book (new), seeded from each team’s history once; events keep their own copy of name/address/diamond so nothing already recorded changes.

Trade-offs

  • Dropdown over pills for arrival — one shape across every form; the fifth case needs the clock either way.
  • No hard “1 hour before” on every game — the team default is where that belongs; a game a coach never touched should not promise a family a time.
  • Editing a place’s address does not silently rewrite past events; it offers to update upcoming ones.

Size

Arrival: small, client only. Places: medium — a table and its API, the picker and two small sheets, the history seed, the import match, help.

Full plan — Arrival as a lead time, and a place the team keeps

Ruled 2026-09-21 · built on dev 2026-09-21 · source: docs/projects/active/COACH_ARRIVAL_AND_PLACES_PLAN.md

Why

Two asks from the first look at the rebuilt form. What the code did: the Recent chips carried the address of the most recent event with that name (usually blank — on 2026-09-21 not one event on either database held an address) and never the diamond; the org venue library is admin-only; arrival is a clock the native picker opens at the current time of day.

What was built

  • Migration 307 — the place book table (per team, one name per team case-insensitively, the tag book's access rules), a link from each event to its place (the event keeps its own copy of name / address / diamond), the team's two arrival habits (minutes, from the same seven answers), and the seed: every team's distinct location became a place and every matching event was linked (dev 32 places / 170 events; prod ≈16 / ≈118). Applied to dev; prod-owed with the promote, before the code.
  • Arrival — a dropdown of lead times with the clock beside each and "A specific time…" opening an hour before the start; a preset follows a start change, a specific time stays; new games and practices start at the team default. The stored value is unchanged, so the event page, the game-day header and the calendar export read exactly as before.
  • Team Settings → Schedule — "Arrive before a game / a practice", saved on change.
  • Location — type to find a place (most recently used first, with event counts), add one inline (name, address, usual diamond, note), Manage places inside the list; a free-typed location still saves as text. Picking fills the address and the diamond (the diamond only when the game has none). The Recent chips retired; the Address field left the form except on an event from before the book that holds one with no place.
  • More → Field / Diamond # says when it is the place's usual and that changing it is this game's own.
  • Manage places — edit (with the offer to update upcoming events' name and address; never the diamond, never a past event) and remove (events keep their text).
  • The event page shows the place's note under the location.
  • The import matches a row's location to a place and takes its address and diamond where the sheet is silent.
  • Help — the game-day-details article's Arrival term and its Location sub-topic ("the places your team keeps"), the schedule article's Adding-an-event paragraph, a Schedule sub-topic under Team settings; search words for places, venues, arrive before.

Verification

Typecheck clean; the changed-files gate clean (unit suite incl. 11 new tests on the arrival maths and the place rules, spelling, CSS, dictionary, migrations parity with the dev-only divergence accepted as prod-owed); rendered check on the schedule clean (the settings screen's 24 new findings are all on the documents-look card and the help button — not this pass's). Owner walk §214 on the QA tab.

Not built, on purpose

  • No org-level venue library for coaches.
  • No merge of two places (rename covers a spelling; the unique name blocks a duplicate).
  • No arrival default on tournaments or team events.
