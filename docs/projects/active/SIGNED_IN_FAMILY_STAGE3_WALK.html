A second parent’s email on the house-league sign-up

Written 2026-11-04 for Stage 3 (committed bacf24a9b and 7db797940, with the /simplify and /review fixes). One purpose: a parent adds the other parent’s email on the sign-up, and that second parent hears what the first parent hears, the club can see and fix it, and nobody else is reached by accident.

What this walk is for

Before this build the club’s emails about a child reached one parent. Now the sign-up form has an always-visible box, Second parent’s email, with no name asked. That address gets the club’s emails about the sign-up, each as its own message, except payment receipts, which stay with whoever paid. The second parent’s first email says who added them and how to come off. The registrar can add, change or clear the address on the sign-up’s record, add it on Add registration, see it in the contact-details export and find it by search. The club’s Email families reaches both parents of a household and counts the household once. The coach sees it. The address is never a household key and never reaches a marketing list.

It passes when

  • The sign-up form takes a second parent’s email, refuses the first parent’s own address and a malformed one in words, and with the box empty behaves exactly as before.
  • Both parents get the sign-up confirmation, each once, and the second parent’s opens with “Hi,” and the line saying who added them.
  • Approve and Decline reach both parents; a team email reaches both; “Email families” reaches both and counts one family.
  • A household that has a sibling sign-up without a second parent never sends that second parent a message naming the sibling.
  • A card payment’s receipt goes to the payer only.
  • The registrar’s record window, Add registration, export and search all carry the address, and the coach’s roster and Copy emails include it once.
  • Every screen reads well at 390 px and at a desk.

Not in this walk

  • A parent editing the second address themselves. That waits for Stage 4 (signed-in accounts); today only the registrar changes it.
  • A club-customised confirmation email. A customised template cannot carry the “who added you” line, so the second parent always gets the built-in email. Unit tests pin it; no dev club customises it.
  • The first email being edited to equal the second. The refusal is worded and unit-tested; the record window’s first-email edit is not part of this stage’s drawn screens.
  • The counsel review (PIPEDA / CASL). It gates Stage 4. Nothing here waits on it.

Before you start

Dev server
Running on a build that includes the Stage 3 commits. If you started it before bacf24a9b landed, stop it and run npm run dev. Part S shows you whether it is the new build.
Email
RESEND_API_KEY is set in .env.local and NEXT_PUBLIC_APP_URL=http://localhost:3000. Without the key a send is skipped and every “inbox” step fails.
Your inboxes
Use your own plain address with plus tags (call it you@gmail.com): you+sp1@ is the first parent of Walk Alpha, you+sp1b@ is Alpha’s second parent, you+sp2@ is Walk Beta’s parent, you+sp2b@ is Beta’s second parent added later, you+sp3@ and you+sp3b@ are Walk Gamma’s two parents, you+sp4@ and you+sp4b@ are Walk Delta’s, and you+sp1pay@ pays in Part I. The dev .local addresses cannot receive mail.
Reruns
A child is refused as a duplicate with the same first email, and an address is limited to 8 sign-up attempts an hour. On a second run use new tags (+sq1 …).
Email not there?
Wait 2 minutes, then look in Resend › Emails and search the address.
When done
Part Z: tell Claude “second parent walk done” and it removes the walk’s sign-ups.
