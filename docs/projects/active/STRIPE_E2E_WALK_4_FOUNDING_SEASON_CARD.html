Card on file and choosing next season (Founding Season clubs)

Written 2026-10-28. One purpose: with real Stripe, prove a Founding Season club can save a card without being charged, choose its plan for next season without being charged until the date the screen shows, change its mind, and remove a card. Both screens were walked before (§150 and §155) but only with a pretend checkout.

What this walk is for

A Founding Season club (a club whose first season is free) is asked, in the summer, to put a card on file and to choose its plan for the next season. The promise printed on the screen is that nothing is charged before the date the screen shows. The two earlier walks (§150 and §155, September 2026) ran on your own computer with the billing mock switched on, so Stripe was never called, no webhook ever fired, and the card on file was proven only from a seeded row.

This walk uses the real Stripe checkout and the real webhooks on the dev site. It checks four things in Stripe itself: the saved card is attached and nothing was charged; the plan choice becomes a subscription that starts later (a trial that ends on the first-charge date) with nothing paid; changing the choice leaves exactly one live subscription; and removing a card is picked up by the webhook.

It also asks you to rule on three things the code does that you may not expect: where the owner lands when Stripe sends them back, what happens if they start to change their choice and then walk away, and what a card that will fail later looks like when it is saved.

It passes when

A card can be saved with no plan and no charge, and a declined card saves nothing. The choice creates one subscription in Stripe that is Trialing until the first-charge date with no payment taken today, the screen names the plan, cycle, amount, card and date, and the club’s plan does not change. At every moment the Stripe customer has at most one live subscription for the choice. The Billing webhook shows a 200 for every event this walk causes. Everything the code sends or does not send (return page, emails) is ticked as you saw it.

Where
Everything is on https://dev.fieldlogichq.ca (the dev site), in a normal browser window. The Stripe dashboard is in test mode (“FieldLogicHQ sandbox”) in a second tab, and Resend › Emails in a third. No real money moves.
The one thing that must be true first: the card window

The card, the “Choose your 2028 plan” card and the “Add payment method” button only appear in the summer card window. By the code’s own calendar that window opens on June 1, 2027, so today the dev site hides all of it unless the site was built with the date moved earlier. The earlier walks did that on your own computer with the setting NEXT_PUBLIC_FOUNDING_SEASON_CARD_WINDOW_OPEN=2026-01-01T05:00:00.000Z.

For this walk the dev site needs that same setting in its Amplify environment (it is read when the site is built, so the dev branch must be rebuilt after it is set). Whether it is set is not something the walk can see from outside: step A1 checks it and stops you if it is not. The setting only moves a display date; the server and the page read the same one.

Which club

Its Plan & billing page is https://dev.fieldlogichq.ca/uat-plus-org/admin/tournaments/settings/subscription (for a Tournament Plus club that is the address, not /admin/org/billing). The sign-in below also owns UAT Test Org and UAT Club Org: always check the page names UAT Plus Org.
The rule being tested
The first charge is the day the free season ends, which the screen prints as one date (“the date the screen shows”). In the code today that date is the start of the day after the Founding Season ends, October 1, 2027, derived from one setting — not January 1 as older notes said. This walk never types a date: it checks that Stripe’s trial end and the first invoice fall on the date the screen shows (a dashboard set to a time zone west of Toronto may show the evening before, which is fine).
Finding the right Stripe customer
UAT Test Org’s Stripe customer has the same email as this sign-in, so searching by email shows two. Use the newest one, whose Metadata contains an orgId. It is created at step B1 and re-used for the rest of the walk.
Test cards
Approved: 4242 4242 4242 4242. Declined: 4000 0000 0000 0002. 3-D Secure (asks for a test authentication): 4000 0025 0000 3155. Saves fine but fails when someone charges it later: 4000 0000 0000 0341. Any future expiry date, any three digits, any postal code. Stripe’s page also asks for an email and a name: any will do.
Webhooks
Stripe dashboard (test mode) › Workbench › Webhooks › the destination named Billing › Event deliveries. After each step that touches Stripe, the named event types should appear within about a minute, each with a 200 next to it.
Emails
Nothing in the card or choice flow sends an email in the code today, and the sign-in’s address cannot receive mail anyway. Part F checks Resend › Emails (it lists every send attempt) so you can rule on it. The summer reminder emails are scheduled campaigns and are not triggered by anything here.
What this walk leaves behind
A Stripe customer for UAT Plus Org with cards and a live plan-choice subscription, and the club’s saved card and choice. Part G puts the club back to “no card, no choice”; the Stripe customer itself stays and is re-used next time.
