Teams run short, and the product has no word for it

A player gets sick on Friday, two families are away, and Saturday needs nine. So the coach borrows one — from the club's other team, from the level below. Minor sport calls this a call-up.

"we need to have the ability to add 'call up' in our games to see them in lineups and such. we don't want them cluttering up our screens that have roster lists where it is not applicable (i.e. player dues, skills and goals, etc.) but also need them available for things like making rosters and what not. at a minimum they need to be available for lineup construction"
— the owner, 2026-09-22

What a coach does today

One of three things, and all three are bad. Add them to the roster — and now they are on the team: dues, skills & goals, awards, the season report, family emails, and they roll into next season. Leave them out — and the builder's lineup is not the lineup being played. Keep it on paper — the worst one, because then the printed card, the bench console, the game notes and the report are all working from a fiction.

Two finds that set the shape

Both came out of reading the code rather than the ask, and each one changes what gets built.

What the build turned up

Four defects, none of them in the request, all fixed. Each is a screen that would have been wrong in a way nobody would have reported as a call-up bug.

B1

Found while building: the bench console silently deleted call-ups from a saved lineup

Fixed

The console trims a saved lineup down to the players it was handed — on purpose, so a player deactivated mid-season cannot poison every save. Call-ups were not in that list, so the console dropped them on load and the next substitution wrote the lineup back without them. Mid-game, no error, a real player gone from the card.

B2

Player dues would have listed every call-up at /usr/bin/bash — the first screen the request named

Fixed

That screen deliberately reads the whole roster, because a player who left mid-season can still owe money — so it inherited none of the free exclusion every other money surface got. Caught by the new guard rather than by reading.

B3

Re-opening a saved game dropped its call-up from the batting order

Fixed

The builder looked its saved players up against the roster alone, so a call-up resolved to nothing and was quietly filtered out — leaving a hole in the order and a card that no longer matched the game.

B4

The player profile would have offered to move a borrowed player onto the roster

Fixed

That page carries the Take them off the roster control, which flips the very field that makes someone a call-up. It now refuses to open for one, and the roster save refuses the value outright.

Two finds that set the shape

Both came out of reading the code rather than the ask, and each one changes what gets built.

F1

A call-up in the season report would tell the coach a lie

Critical

The season playing-time report is the most trusted screen in the lineups area: it catches a kid being short-changed on field time. It is driven by saved lineup entries. A call-up admitted naively lands in the fair-play table like this, beside teammates with a full season behind them:

FAIR PLAY — season to date #7 Morgan 14 games 58 field 26 bench #12 Riley 14 games 55 field 29 bench #3 Avery 13 games 51 field 31 bench #22 Jamie (call-up) 1 game 4 field 2 bench ← reads as neglect

The rule this sets, and it is the binding one: a call-up counts inside a game and never across the season. The game's own checks — everyone bats, coverage, the pitching cap, Mark ready — must count them, because they are really out there taking a slot. Every season-long figure must not.

F2

A call-up attached to the season re-creates the clutter it was meant to remove

High

If a call-up is simply "a different kind of player on the team", they sit in the available list of every game for the rest of the year. Four across a season means four extra names in every lineup builder forever, and the coach has to remember which one is actually coming on Saturday. The ask said it already: "add call up in our games". So the primary object is an appearance — Jamie is called up for Saturday — with a saved pool underneath so nobody retypes Jamie every week. The appearance count comes free, and several leagues cap how many games an affiliate may play.

F3

Found on the way: a roster state the product can render and the database can never produce

Medium · unrelated, rides along

The roster status type carries three values; the live constraint allows two. Nothing writes the third, and two surfaces read it — the closed-season page renders "Left during the season" for a state that cannot exist.

type RepRosterStatus = 'active' | 'inactive' | 'released' live status = ANY (ARRAY['active', 'inactive']) ← 'released' is unwritable

It is a dead branch, and it is exactly the mistake this feature must not repeat: a status value added to the type without the constraint change is a value the product shows and the database refuses. Retiring it rides with this work.

What the code does today

Read out of the working tree and the live dev schema on 2026-09-22. This is the evidence the model choice rests on, and it is unusually favourable.

One roster table, 24 dependants

Every player-shaped thing in the portal hangs off one table — attendance, lineup entries, game moments, dues, payments, awards, documents, observations, goals, baselines, family links. Any model that puts a call-up elsewhere has to answer all 24.

~59 roster reads already screen for "active"

Lineups, attendance, the console, awards, development, dues, practice plans, templates, tryouts, insights, the recap, Wrapped, the settlement, the rollover. Every one of them.

Two writes go further and reject

The lineup save refuses any id outside the active set; the attendance save answers 400 — "Attendance can only be saved for active roster players". That is the guard this feature opens, and it must be opened narrowly.

The consequence, and why it decides the model

If a call-up is a roster entry that is not active, then all ~59 of those screens exclude them the day the change lands, with no code touched — and so does anything built next year. The feature fails safe: a surface we forget hides a call-up.

The seven places that do the opposite test — these fail open

Seven roster-scoped places ask for the ones who aren't on the team. Each needs a deliberate answer, because each would otherwise show a call-up alongside departed players.

SurfaceWhat it asks for todayWhat a call-up would wrongly do
Roster page — off-roster liststatus !== 'active'appear under "off the roster" beside departed players
Roster page — reorder tailstatus !== 'active'be re-ordered as though departed
Player profile — not-active bannerstatus !== 'active'wear a banner written for a departed player
Closed-season page — roster shelfstatus !== 'active'appear in the archived roster, labelled "Not active"
Development session — departed with readingsstatus !== 'active'— safe (a call-up never has readings), but assert it
Season settlement — the departed flagdeparted: status !== 'active'— safe by accident (the loop runs over dues rows and a call-up has none). Gets an explicit guard.

Also on the audit list: 55 queries touch the roster table directly and only 10 carry a status filter. The other 45 are single-row reads by id or writes — not a hazard on their own, but each gets checked rather than assumed.

Three models, and why one wins

A · A roster entry of a different kind ✅

A call-up is a roster row that is not active. All ~59 filters exclude them free, all 24 foreign keys keep working, and it fails safe. Cost: the seven sites above need answers, and "this call-up is inactive" becomes inexpressible — which it never needs to be. You remove a call-up; you don't retire one.

B · A tick-box on a normal player

Tidier in theory and wrong on the only axis that matters. All ~59 filters would include call-ups from the moment it lands — in dues, in skills & goals, in family emails, in the fair-play report — which is the clutter the ask is about. It fails open, and so does every screen built after it. Rejected.

C · A separate call-up table

Cleanest identity; breaks the one thing the ask is about. Lineup entries, attendance, notes, the grid, the generator, the analysis, the caps, the printed card and the console all key on a single player id. Model C means every one of them merging two lists. Rejected for v1.

Where a call-up appears — and where it never does

The right-hand column is the actual feature. Anything that moves money, judges a player, reaches a family, or measures a season is on it.

In the game

  • The lineup builder, for the game they were called up to — under their own Call-ups heading
  • The batting order, the field grid, the per-inning list
  • The per-game lineup check and Mark ready — everyone bats, coverage, clashes
  • The per-game pitching cap (pending R2)
  • The printed lineup card, game sheet, poster and PDF
  • The bench console — on the field, on the bench, in a swap
  • Game notes and moments — they made the play
  • That game's attendance sheet, and no other (pending R4)
  • A quiet Call-ups section on the roster page — name, number, games played, remove

Never

  • Player dues, the budget plan, the installment generator
  • Fundraiser credit, payouts, refunds, the season settlement
  • Skills & goals, development sessions, observations, evaluations, continuity
  • Awards · documents · measurables
  • Tryouts and baselines
  • Family emails, practice-plan sends, the family portal
  • The roster count and every "your team has N players" figure
  • Every season-long playing-time figure — fair play, bench balance, position variety, season arm care
  • Season insights and the digest · the player season recap · Season Wrapped
  • The closed season's roster shelf
  • Next season's rollover

The one deliberate exception

A saved lineup card from a game they played keeps their name — including in the closed-season archive. A call-up is not on the archived roster, because they were never on the team; but the game happened, and an archive that quietly drops a player who was on the field rewrites the season. That is the one thing an archive must never do, and it is the same rule that keeps a departed player's name on the record today.

Six rulings — all ruled as recommended

Owner, 2026-09-22: “I agree with your recommendations.” Every option marked below is the one that was ruled and built. Kept in full because the reasoning is the record of why the feature has the shape it has.

R1

The word

Whatever is picked gets locked to one spelling across every screen, table heading, button, toast, error, help article and help search term — and enforced by the build. Worth settling now rather than after it is in forty strings.

A · Call-up Recommended

Capital C, hyphenated. Plural Call-ups. The action reads "Call up a player". Sport-neutral and plain.

B · Affiliate / AP

Precise in baseball and hockey governance, and reads as paperwork. AP is jargon a new coach won't know.

C · Pick-up

Natural speech, but collides with "pick-up game" — a different thing entirely.

D · Guest

Understates it. A guest watches; this player bats.

R2

A call-up who pitches

The product tracks a per-game innings cap for arm care, and a season-long arm-care report. A borrowed pitcher sits awkwardly across the two.

A · Warn in the game, not in the season Recommended

The per-game cap warns as it would for anyone. No row in your season arm-care report.

B · Both

Puts a one-game pitcher in a fourteen-game report — the F1 problem again, in a different table.

C · Neither

Silent while a borrowed child throws over a cap. Not defensible.

Why A: you are responsible for that arm on that day, so the warning has to fire. Their innings are not your season's record — and their own team's cap is not something this product can see.
R3

Attached to a game, or to the season

A · Per game, plus a saved pool Recommended

A call-up shows in the game you called them up for. The pool means you never retype a name. Appearance counts come free.

B · Season pool, shown in every game

Cheaper to build and it decays: by August every lineup builder carries every call-up you used in May.

Why A: B re-creates the exact clutter this feature exists to remove — see finding F2. It is one small link between a player and a game, and it is what makes the feature feel right rather than merely present.
R4

Attendance

A · That game's sheet only Recommended

Present on the game they were called up to; on no other event, ever.

B · Never on an attendance sheet

Simpler, and a call-up who doesn't turn up is exactly the problem attendance exists to record.

R5

Who may add one

A · Anyone with lineups access Recommended

Including assistants. It is a decision made at a field, often by whoever is running that game.

B · Head coach and standalone only

Matches the roster-write rule, and blocks the assistant standing at the diamond an hour before first pitch.

C · Anyone with roster-write

Same objection as B, with a less obvious rule.

Why A: a call-up creates no money, no evaluation and no record that outlives the game. The permission should sit with the job, and the job is building a lineup.
R6

Contact details on a call-up

A · A phone number, never an email Recommended

Optional. Enough to reach someone at the field, and structurally incapable of entering an email audience.

B · The full guardian block

Every guardian field the roster has — and one missed audience filter away from emailing a family that isn't yours.

C · Nothing

Safest, and leaves a coach with a borrowed child and no way to reach anyone.

Regardless of the answer: a call-up never enters a family audience, a practice-plan send, or the family portal. That is a hard rule in v1, not a preference.

The build

Phase 1 is the whole ask. Phases 2 and 3 are worth doing and worth doing after.

Phase 1 — the floor

The ask, in full
  1. The database learns the new kind of roster entry, and the per-game link — in a migration, which is the lesson of finding F3.
  2. The lineup builder gains a Call up a player action and a Call-ups group under Not in the lineup.
  3. Every row a call-up appears on carries the mark.
  4. A game's lineup admits exactly the call-ups linked to that game — not the pool, not every borrowed player.
  5. The printed card, game sheet, poster and PDF list them, marked.
  6. The seven fail-open surfaces each get their answer.
  7. The dead released state is retired.

Phase 2 — game day

Next
  1. The bench console: on the field, on the bench, in a swap.
  2. Game notes and moments.
  3. That game's attendance sheet.
  4. The appearance counter on the pool, for leagues that cap borrowed games.

Phase 3 — the club

Later, and worth waiting for
  1. When the club runs both teams here, pick a call-up off the other team's roster instead of retyping the name — so a real child does not become a duplicate record.
  2. This rests on the person layer that already exists underneath the roster, and deserves its own pass.

What gates it

  • One assertion per excluded surface, by name — dues, the installment generator, skills & goals, awards, documents, tryouts, family audiences, rollover, settlement, Wrapped, the digest, the player recap, the archived roster shelf. F1 being free today is not the same as it being held next year.
  • The F1 rule, asserted from both sides — absent from every season figure, present in the per-game check.
  • The narrow hole — a lineup save accepts a call-up linked to this game and rejects one linked to another.
  • The guard that would have caught F3 — the roster status type and the live database constraint must agree.
  • The 45 unfiltered roster queries audited; the word added to the spelling gate once R1 lands; help content updated in the same unit of work; layout sweep, full suite, typecheck.
