Board Ready, Stage 1. Parents name friends at sign-up, the registrar confirms each one against this season's sign-ups, and the draft keeps confirmed friends together in groups of up to 3. Example data, made up for the drawing: Milton Bats Softball Association, 2027 Summer House League, the U9 division. Every frame is drawn at true size. At the maximum, finished friends fold to one line each, and a tap opens one again. Whether they fold is a build detail, not an ask.

Why under the division line

The form already works out the child’s division as the parent types the birth date. Placing the question after that line lets the help text say “signing up for U9”, which heads off most cross-division requests without the form checking anyone.

It is not hidden under “Jersey number, position and notes”. A request the parent can’t find ends up in the notes box, which the draft can’t read.

What is never shown back

  • Whether a named child has signed up.
  • Which division a named child is in.
  • The name behind a friend code. A typed code shows only as the code.

Each of these would let an anonymous visitor test whether a child is registered with the club.

The friend code field

Six characters, grouped 3 + 3, with no 0, O, 1 or I. The sixth is a check letter, so the form catches a typo (“That code has a typo. Check it with the other family.”) without looking anything up.

Build: the form’s own inputs, its “Remove” word link (as on Child 2) and its secondary button (as “+ Add another child”). Friends are hairline blocks inside the child’s section, never nested cards.

The family passes it on however they like: a text message, school pickup, a group chat. Copy puts it on the clipboard, and that is all it does. Brothers and sisters each get their own code, because requests are per child.

Where else the code appears

Why a code is safe to hand around

Whoever holds a code learns nothing from it, because entering it on the form shows no name. It only links two children for the registrar, and only when entered on a sign-up in the same season.

3 · The club’s settings, in the two places settings already live

Correction to the brief. The prompt asked for a “season’s house-league settings” screen, with the new switch “beside Families together”. Neither exists as described. A season’s settings are the blocks on its Overview tab, and “Keep families together” is not a stored setting. It is a switch inside the Run the draft window, on by default, shown only when a division has brothers and sisters.

So the maximum per child goes in the Overview’s Registration block, because it changes the sign-up form. The Keep friends together switch goes in the draft window beside Keep families together, because it changes one draft.

Warn, never block

Requests still to confirm don’t stop the draft. The Friends row says how many and links to them, the way “Not drafted” already links to Registrations. The convenor chooses. This follows the plan’s “warn, never block” ruling (Q4).

When the switch appears

Like Keep families together, the friends switch shows only when the division has at least one confirmed request. Otherwise it is absent, not greyed out. It is on by default, and the choice holds for the visit, so Draft again uses it.

How a match is found

  • Only this season’s sign-ups. Same division first. A match in another division shows only as “Different division”.
  • Names are compared ignoring capitals, accents, hyphens and apostrophes (José = Jose, O’Brien = OBrien). Today’s matcher ignores capitals only, so it needs widening.
  • A first name that starts the other (“Jon”, “Jonathan”) counts as similar.
  • The parent’s name, when given, ranks the matches and is shown as the reason.

A match never confirms itself. Even Both asked waits for Confirm.

The two marks

Code match: the other family’s code was entered. It is exact, so it arrives in Confirmed. The registrar can still undo it from ⋯.

Both asked: each family typed the other child’s name. It is the strongest name match, so the pair is one row at the top and one Confirm covers both. A code covers the other direction too: if Liam’s family typed Maya’s name and Maya’s family entered Liam’s code, both requests read Confirmed.

120 requests, and deleting one

The registrar who did this in Excel works down “To confirm”. Selecting rows and choosing “Confirm best match” confirms a whole page at once, still as the registrar’s own decision. Rows with no single best match (Pick one…, Not signed up, Can’t honour) are left out of it.

Delete request… in ⋯ removes one request completely. That is how the club answers a family who asks to have a name removed.

Splitting a group

The player’s ⋯ menu gets “Keep apart from a friend…”, which asks which friend. The draft and Draft again then treat that request as split, and it reads Not honoured · kept apart by {name}. “Keep together with {friend} again” undoes it. A split is a decision about the draft, so it belongs on the board, not in the queue. The popover only lists names, as the family popover does.

Moving a player by hand splits nothing. The request reads Not honoured until the player moves back.

Groups and the cap of 3

  • A group is every child joined by confirmed requests, plus their brothers and sisters.
  • A group that would pass 3 keeps its strongest links: Both asked first, then code matches, then the earliest confirmed. The rest read Not honoured · the group would pass 3.
  • The cap never splits brothers and sisters. A family of three has no room for a friend.

Who sees the marks

The friend mark, its popover and the filter show only to people who can open Registrations, the same rule as the family note (ruling A8). Anyone else running the board still gets the groups kept together, without seeing who asked for whom.

Build: the sibling mark’s button, popover (SheetFrame on a phone) and lit row; the lucide Handshake icon; FilterMenu’s Show only group; CoachToolbarMenu for ⋯.

What B changes beyond the row

  • Today’s family mark becomes the Together mark: same symbol, same popover and lit rows, now listing family and friends together, each labelled.
  • The filter keeps both “Has a sibling in this division” and “Has a friend request”, so either can still be found on its own.
  • The board’s other second-line states (Locked, Moved by you, Not told) are unchanged.

Why B over A

A is tidy but still asks the convenor to read two numbers that mean the same thing to the draft. B answers the question the convenor actually has, “is anyone separated from who they should be with?”, in one amber mark. It also leaves the name a little more room.

A is the safer choice if you want friends visibly distinct from family at a glance.

Who sees what

Rating, notes and the Together count for friends follow today’s rights: RTG only for people who see ratings, and notes and friends only for people who can open Registrations. A place a reader can’t see is absent, not empty, so their row closes up.

Build: the row’s columns already come from the reader’s rights; this adds one fixed place per mark kind and a heading row symbol for each.

Formatting check (portal standard)

  • Headings in the display face, uppercase, secondary ink. The name is the row’s target, with one chevron column, only where a row opens.
  • One row action per row (the Registrations recipe: olive outline), the rest behind ⋯. No links inside cells.

  • Waiting counts as the amber pill: To review and Friend requests. The other views’ counts are the lighter ink, and a zero is not drawn.
  • One lime per window (Confirm, Run the draft). A decline is outlined. The toolbar has no lime.

What the /legal review changed in these drawings
  • The form’s privacy line now says what is true. More than one seat sees the names, and deletion has a defined trigger (A12), which the stage must build. Nothing deletes on its own today.
  • A caution line: “Only name a child whose family is happy for you to.” A typed name can belong to a child who is not a member, and that family is never told.
  • One audience rule everywhere: the seats that can open Registrations (A11).
  • “Delete request…” in ⋯, so the club can answer a family that asks to have a name removed.
  • Friend names are kept out of the contact-details export; the Friend requests export carries children’s names only.
  • For the build: typed names are used only for team placement. No outreach to a family that hasn’t signed up, and a name never feeds the families or people lists. Requests belong to the season’s sign-up, not to the child’s cross-season record, so deleting them is clean.
  • For a lawyer, if you choose: reading a non-member child’s name as indirect collection, and the exact notice wording. Québec’s Law 25 is re-checked when the first Québec club signs.

A1 · Can the club change the group cap of 3, the way it sets the maximum?

Recommend: no, fixed at 3 for the first release. The cap protects team balance; its only job is to stop friend chains from swallowing a team. A club that raises it to 5 gets teams that come out uneven, and the draft window then explains why every time. A setting can be added later at no cost, but taking one away from a club that uses it is costly. The cap is printed in the settings and in the draft window, so it is never a surprise.

A2 · A request for a child in another division: allowed at sign-up, or refused there?

Recommend: allowed at sign-up. It arrives in the queue marked “Different division”, with Can’t honour as the row’s action. Refusing it at sign-up would mean the anonymous form telling a stranger that a named child is registered in another division. Instead, the form names the child’s own division in its help line (“friends who are signing up for U9”), which heads off most of these.

A3 · When a requested friend withdraws, or a request changes after the draft, what does the registrar see?

Recommend: the result is read live from the teams, and nothing re-deals by itself. A withdrawal reads “{Friend} withdrew {day}”. A request confirmed after the draft reads “Confirmed after the draft” until the convenor moves a player by hand, and then it flips to Honoured. Families can’t change requests once their division’s teams are made (A5), so there are no late edits from families.

A4 · Do friend requests import from a TeamSnap or CSV registration export?

Re-framed: there is no house-league registration import to add a column to. The prospect club moves off TeamSnap by taking next season’s sign-ups on our form, where the question lives. If a registration import is ever built, a “Plays with” column should land in this same queue as typed names: suggestions, never confirmed. Recommend recording that as a rule for any future import, and not building an import for this stage.

A5 · New: can a parent add or change friend requests after signing up, on “Your sign-up”?

Recommend: yes, until that child’s division has its teams made. The family that signs up first can’t enter a code that doesn’t exist yet, so without this the code only ever works one way. “Your sign-up” already lets a family ask to withdraw, so a small change form fits there. Once the teams are made, the Change link goes and the page says “Friend requests closed when the teams were made.”

A6 · New: does the cap of 3 ever split brothers and sisters?

Recommend: never. Keep families together already keeps a family whole, whatever its size. The cap limits only friends joining a group: a family of three has no room for a friend, and a family of two has room for one.

A7 · New: when a chain of requests would pass 3, which links are kept?

Recommend: Both asked first, then code matches, then the earliest confirmed. A request both families made is the strongest signal. The rest read “Not honoured · the group would pass 3 children”, so the registrar can see them and fix one by hand.

A8 · New: what choices does the maximum offer?

Recommend: None (don’t ask) · 1 · 2. With a group cap of 3, a child plus 3 friends is a group of 4, so a third friend could never be kept together. Offering 3 would invite requests the draft can never honour. If A1 goes the other way (a club-set cap), the maximum’s choices follow the cap.

A9 · New: the friends switch goes in the draft window, not a stored setting. Agreed?

Recommend: yes. The brief imagined a settings screen with Families together on it. In the product, Keep families together is a switch in the Run the draft window, and Keep friends together belongs beside it. The one stored setting is the maximum per child, because it changes the sign-up form.

A10 · New: does the confirmation email carry each child’s friend code, as text?

Recommend: yes, as text, never a link, in a neutral sentence: “If another family wants {child} on their child’s team, they can enter this code on their sign-up.” That is the moment the family is thinking about it, and a parent can forward an email easily. /legal finds it transactional under CASL as long as it carries no “tell a friend” push. A sent email is outside the season-end deletion, which is acceptable because a code reveals no name.

A11 · New: who sees friend requests?

Recommend: the same seats as family notes, the people who can open Registrations (ruling A8), on every surface: the queue, the record, the board marks, the after-draft result and the export. A typed name can be a child who isn’t a member at all. The draft still keeps groups together for whoever runs it. Only the marks and the names are held back.

A12 · New: when are requests deleted?

Recommend: when the club marks the season finished, or 60 days after its last day if it never does. The deletion is built in this stage, because the form promises it. “Registration closed” can’t be the trigger. It comes before the draft. Some seasons also sit past their last day without being marked finished. Typed names, codes, matches and keep-together groups go together. The export is the club’s own copy, and the Friend requests screen says so.

Option /legal raised: delete the typed names and parent names sooner, 30 days after the division’s teams are made, keeping only a name-free Honoured / Not honoured until the season ends. More private, but the registrar loses the “what did they type?” column once the season is under way. Recommend the single trigger above. Say if you want the earlier one.

A13 · New, from the /design review: Friend requests as a fifth view on Registrations, with its own amber count?

Recommend: yes. The four-view switch was ruled for four views of one list (13i Ask 6), and requests are a different record. But a registrar does this work while working through sign-ups, the switch already scrolls on a phone, and a separate door would be one more place to look. It carries the amber waiting count beside To review’s, and it is absent when the club asks for no friends.

The same review’s other proposals are drawn in, for your yes: a Both asked pair is one row and one Confirm; Can’t honour is an outlined button, not lime; the split moved from popover buttons to the player’s ⋯ menu; the parent’s name stays off the export.

A14 · New, from your round-1 note: how should a player row lay out its marks?

Recommend B: one “Together” place (family and confirmed friends), then note, then money, each in a fixed place headed by its symbol, and amber when someone in the group is on another team. To the draft, family and friends are the same thing, a group capped at 3, and the only case a convenor acts on is a separated group. A gives every mark kind its own column and keeps friends visibly distinct from family. It is the choice if that distinction matters more to you than one signal. Either way the marks line up down a team, and the card is wide enough at its real size (about 390px, two cards across).

A15 · New: a heading over the rating column?

Recommend “RTG”, with a hover that says “Rating: 1 is newest to the sport, 5 among the strongest”. “RK” reads as rank, where 1 is best, and here 5 is strongest. A full-name hover isn’t needed, because names wrap rather than cut off on the real board (my drawing cut them off). The heading shows only to people who see ratings, as the column does today.
