## Confirmed finding

**[Medium, existing] `app/api/platform-admin/bookkeeping/owner-movements/route.ts:67` — repayment limits are checked before a separate insert, so concurrent requests can exceed an expense's business amount.**

Verdict: **Confirmed**, high confidence. Two distinct reimbursement IDs can both read the same prior movement list, both pass line 69, then both append at line 73. Per-movement revision uniqueness protects competing changes to the same movement, but does not serialize different movements for one expense. The same read/write separation exists between an expense correction/Void's linked-reimbursement check (`expenses/route.ts:82`, `:126`) and its insert (`:83`, `:173`), so an expense change can also race a new reimbursement. The second cross-route interleaving was reviewed in source, not executed.

Reproduction: `.probe/bk-stage1/part6-race-proof.mjs` invokes the actual transfer POST handler with mocked auth and storage. A barrier gives two $15 requests the same empty repayment snapshot for a $20 personal expense. Both return 201 and append $30. `.probe/bk-stage1/part6-race-results.json` records `[201,201]`, 2000 expense cents, 3000 accepted reimbursement cents, **zero external writes**. The identical repayment check/insert separation exists in the baseline `7c4e0081f`; Stage 1 did not introduce it.

Fix recommendation: enforce the aggregate repayment invariant in a database transaction with a common per-expense conflict boundary shared by both APIs; retry conflicts by rereading all relevant current records. Cover two competing reimbursement IDs and reimbursement versus expense amount/payment-source change or Void. A browser busy flag or process-local mutex is insufficient across tabs and server instances. This is a recorded real-books readiness prerequisite; no automation, database or API change is included in Part 6. The sequential walk saves one operation at a time and does not claim concurrent safety.
