Club Tier · Stage 4e · Round 1 drawings

Connect the club’s own web address

A club owner connects an address the club already owns, like www.lakeshorelynx.ca, once. From then on the club’s public pages answer there, and every link the product hands out uses it. Sign-in, the admin and the coaches portal stay on FieldLogicHQ. Every club, name, address, date and record value here is an example. All words are provisional: they go through /marketing after you rule, before any code.

⚖ Ruled 2026-10-23

All seven asks as recommended (owner: “I agree with your recommendations”), plus the owner’s call on frame b: the field starts with www. already written and unable to be deleted. Build prompt: CLUB_TIER_STAGE4E_BUILD_PROMPT.md.

What these drawings decide

  • Where the door lives: drawn as its own row, Web address, on the Public site page, just above Visibility (ask 1). Settings and inside-Visibility are shown as thumbnails.
  • One row carries the whole journey. It opens in place like every other row, and its closed summary always says where things stand, so an owner who leaves for a day sees the state at a glance when they come back.
  • No support ticket at any step. The two records appear about ten seconds after the owner types the address. Every peer (TeamSnap, SportsEngine, TeamLinkt) ends in a ticket, an email or a form.
  • The weak spot is said plainly: the address without www has to be forwarded where the club bought it. The row teaches it, links the three common places, and (ask 3) checks whether it worked.
  • Seven asks at the bottom. Three were set by the prompt. Four came out of drawing it, and two of those are real conflicts: the name “Web address” is already taken, and the forward from the old address hides signed-in families’ pieces on every page of that club.

Push back, before the drawings

  1. Settings is the wrong home now (ask 1). The 10-19 ruling said “in Settings”. Since the Public site builder, every public-site control lives on Public site, and Settings is the owner’s alone: an admin cannot open it at all, so an admin could not even read whether the address is working. Settings keeps one public-site thing today, the last part of the FieldLogicHQ address, and that one changes admin links too, so it stays.
  2. “Web address” already means something (ask 5). Settings has a field called Web address (the lakeshore-lynx part), and Visibility shows it under that name. A rule from Stage 5 made it one name on both sides. A second thing with the same name breaks the one-spelling rule. Drawn: one row named Web address that holds both, and the new thing is called “your own address” in sentences.
  3. The registrar login is often not the owner’s (found by the flow check). It sits with a past president or a parent who built the old website. The owner needs to hand the two records to someone else, so the row has a Copy both as a message button. That is also why ask 2 recommends admins can read the records.
  4. Two rulings collide for signed-in families (ask 7). Ruling 4 forwards fieldlogichq.ca/lakeshore-lynx to the club’s address. Ruling 5 hides signed-in pieces there. Together, a family that follows a team can never see Follow, alerts or My team on that club’s pages, tournament pages included (ruling 3), which is where following matters most. Recommended: forward everyone except signed-in visitors. Both rulings’ reasons (posters keep working, search moves over) survive.
  5. “www only” leaves out a club that keeps its own website (ask 4). Many clubs already run a site at www and want only the teams part here, like teams.lakeshorelynx.ca. The www ruling answered the bare-name problem; it did not consider this club. The technology treats any name the same.
  6. Is forwarding enough? Mostly, if it is checked (ask 3). Volunteers used to the peers’ A records will look for numbers we cannot give. Advice alone leaves them unsure it worked. A line in the row that says “Forwards to www” or “Not forwarding yet” turns advice into a result.

Asks

Pick one per ask, or write your own. The box at the bottom collects everything to paste back. The recommendation is the first option in each.

1Where does the door live?

Drawn as its own row on Public site, above Visibility (frame a). Every public-site control moved to that page with the builder; admins cannot open Settings at all, so on Settings they could not even see whether the address works. The row’s summary carries the state (Waiting, Needs attention) where an inside-Visibility part could not.

2Who may connect it?

The owner holds the Visibility switch today and an admin reads it as text. Connecting changes every link the club hands out, so it is the same kind of decision. But the person with the registrar sign-in is often an admin, and the records are not secret.

3Is “forward the bare name” enough?

Volunteers know A records from every peer. Advice alone leaves them unsure whether it worked. A check of the bare name is one web request a day.

4May a club connect a name other than www?

The www ruling solved the bare name. It did not consider a club that already runs its own website at www and wants only the teams part here, like teams.lakeshorelynx.ca. Technically identical; only the bare-name advice is www-only. Both options keep your fixed www. in the field (drawn in frame b); they differ only in whether there is a way past it.

5What is each address called?

“Web address” already names the lakeshore-lynx part on Settings, in Visibility and in tournament settings (one name on both sides, a Stage 5 ruling). Drawn: one row called Web address that shows whichever address families use, and the new thing is “your own address” in sentences. Final words go through /marketing after this.

6Who is told, and when?

Waiting can last a day, and the padlock warning matters months later. The row shows every state; the question is who gets an email.

7Signed-in families on a connected club’s pages

Ruling 4 forwards the old address; ruling 5 hides signed-in pieces on the club’s address. Together a family can never see Follow, alerts or My team on that club’s pages, tournaments included. Forwarding only visitors who are not signed in keeps both rulings’ reasons: posters still work and search engines still move to the club’s address.

Notes for the build (not asks)

  • Record 2’s value is provisional. It is drawn as a name we own (sites.fieldlogichq.ca) so a future change of host needs no club to touch anything. Whether the host accepts that extra step is a five-minute test at the start of the build; if it fails, record 2 shows the host’s own target and the drawing is otherwise unchanged.
  • ALIAS needs the bare name in the connection too. Whether an unverified bare name holds up the www connection is unproven; test it before offering the ALIAS route. A club whose domain is on Route 53 can ALIAS only to the host’s own target, which skips the safeguard above.
  • Check now is our own lookup of the two records, never the host’s status. Found on our side does not mean live.

  • While broken (g3), stop forwarding the old address and hand out the old address everywhere; resume on recovery.
  • An offline site answers the club’s address with today’s offline page. Connecting is allowed while offline, so a club can launch on its own address.
