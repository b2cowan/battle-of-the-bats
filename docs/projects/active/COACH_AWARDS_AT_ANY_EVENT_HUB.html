          Product-manager brief

          Awards at any event

          What changes for the coach

          A coach can give a player an award at any event on the schedule — a practice, a team event like a banquet or pizza night, or a whole tournament — not only at a game. Once the event has started, its window shows the same Awards given section a scored game has: give an award, edit it, remove it. Games are unchanged: they still unlock once the final score is in.

          Wherever an award is shown, it now says what it was for in words the coach recognises: vs Oakville A’s for a game, Practice (or the practice’s own name) for a practice, and the event’s or tournament’s name otherwise.

          Why it matters

          Coaches hand out recognition at practices all the time — hustle, effort, most improved this week — and at the year-end party. Today the portal only lets them attach an award to a scored game, so practice recognition either goes unrecorded or gets logged as a vague “General” award on the report page. The awards a coach gives most often at the youngest ages are exactly the ones the portal can’t hold.

          Customer impact

          • Who: every Premium coach and the staff they let give awards. Access doesn’t change — whoever can give a game award can give one at any event.
          • Where it shows up: the event window (practice, team event, tournament), the Give an award form, the Awards report, the player’s profile totals, the season leaderboard and Season Wrapped’s “most awarded” — all count practice awards automatically.
          • Families: nothing new to see. A family’s season recap already lists award names and dates, and a practice award appears there like any other.

          Tradeoffs

          • Awards unlock when the event starts, not before. That keeps an empty awards box off every upcoming practice. A coach preparing banquet awards days ahead (to print certificates) still records them from the Awards report, as today.
          • On a phone, a practice’s awards sit below attendance — one scroll down with a full roster — so attendance stays first while the practice is running.

          Priority

          Small, owner-requested, no data change. It closes a gap a coach hits the first week of a season, and it rides on the award tools already built and reviewed this month.

          Success criteria

          • A coach gives an award from a practice window in the same two taps as from a game.
          • No award tied to an event ever reads “General” or “vs opponent” anywhere in the portal.
          • Before an event starts, its window is identical to today’s.
          Full plan

          Awards at any event — implementation plan

          Source of truth: docs/projects/active/COACH_AWARDS_AT_ANY_EVENT_PLAN.md. This tab mirrors it.

          Problem / context

          The award record already points at any event (rep_player_awards.event_id → rep_team_events), but three gates and five labels assume a game:

          WhereWhat it does today
          scheduleDrawerDoorsawards: ev.isGame && canManageAwards
          Schedule event windowawardsBlock renders only when isGameEvent
          POST /awardsAn event-linked award needs teamScore + opponentScore — a practice can never pass
          Award hydrationReads only opponent from the event → eventOpponent
          Awards report “For”vs {eventOpponent} else label else “General” → a practice award reads “General”
          Report edit form / schedule give form“For: vs {opponent ?? 'opponent'}”
          describeAwardOccasion“for this game” for every event
          PATCH /awards/[id]“This award is linked to a game…”

          The only recorded reason for the gate (archived Tags & Awards plan) is “can’t award a game that hasn’t been played”. No ruling excluded practices.

          Scope

          1. One unlock rule, pure. awardUnlockState(event, nowMs) in lib/rep-award-occasion.ts: cancelled → cancelled; game kinds → needs-score until both scores exist; any other kind → not-started until startsAt; else open. The POST route and the window both read it.
          2. The door. scheduleDrawerDoors.awards = canManageAwards(caps) — the door is permission; the unlock is the event’s state. Update its doc comment and its unit test.
          3. The window. Games: exactly as today. Any other event: the section renders only when the state is open (no locked box, no cancelled sentence — anti-clutter). Desktop places it after the practice plan / description / resources, directly above the action row; phone places it after the attendance tab content.
          4. One occasion label. awardOccasionLabel(event | null, tournamentLabel): game kinds → vs {opponent} (falls back to the event name); every other kind → the event’s name; no event → the typed label or “General”. Hydration selects event_type, name too and returns occasionLabel (replacing eventOpponent, whose only reader is the report). The schedule give form builds its label from the same helper.
          5. The sentences. describeAwardOccasion takes the event kind: “for this game / practice / tournament / event”. The PATCH route reads the award’s event to phrase it; its label refusal says “linked to an event on your schedule”.
          6. The note example. Game keeps “Diving catch to end the game”; any other event shows “Ran every drill at full speed”.
          7. Help. Retitle the “Awards (games only, once a final score is in)” article; update the “How do I give a player an award?” FAQ (text + keywords); fix existing drift — both say the form “clears right away” for the next award, but Save has closed it since the owner’s 2026-07-12 correction; the Premium summary’s “MVP given out after games”.
          8. Dictionary. rep_player_awards.event_id’s meaning widens from “the game” to “the event” — a field-meaning change, so DATA_DICTIONARY.md updates in the same unit.
          9. Tests. Pure tests for the unlock state, the label and the sentence (every event kind); the doors test flips the non-game case; source-scan tests that pin “for this game” / “linked to a game” wording get updated.
          Out of scope

          Tags on practices (a game-results vocabulary — “record by tag”). A “For” picker on the report’s Give form that lists schedule events (the natural next step for recording banquet awards ahead of time). Showing awards on the practice review page. The games’ final-score rule. Demo narration — the demo re-seeds itself and no tour anchor changes.

          Approach

          Open the door by event state, not a list of kinds: the rule is “an award is for something that happened”, and a game proves it with a score while everything else proves it with its start time. The alternative — a per-kind allow-list — would need an edit the next time a kind is added.

          The label goes in one pure helper read by every surface, because the defect this project would otherwise ship is quiet: each surface would read fine alone while calling a practice award three different things.

          Season rules

          No change. Award writes already require a live season; nothing learns a year, so the history-endpoint guard is untouched. A closed season shows awards on its one page as before.

          Open questions

          None. Phone placement was ruled with the mockup — below attendance (see Decisions).

          Build record (2026-09-25)

          Built to the approved mockup, on dev. Typecheck clean; verify:changed green (4,739 unit tests; spelling, date, dictionary, layout and schema gates). No migration.

          Found while building, fixed in the same unit:

          • A sixth label. The award-type merge’s confirm said “would hold MVP twice for the Sep 21 game” for any event-linked award. It now names the kind — “for the Sep 21 practice”, “for Team pizza night” (describeDatedAwardOccasion).
          • An award was dated from the UTC day. The give route and the schedule’s Give form cut the date from startsAt.slice(0, 10), so anything starting at 8 p.m. Eastern or later was dated the next day — games too, since awards shipped. Both now use the org-zone day (orgDayKey), the platform’s own rule. Dev holds 23 event-linked awards, all on games, none dated wrong; prod was not audited and nothing was repaired.
          • Help drift. The article and the FAQ said the form “clears right away” for the next award; Save has closed it since 2026-07-12. Rewritten with the rest of the awards help.

          Revised on the first look at the build (same day): on a phone, a started practice’s awards moved from below attendance to above it — the owner asked why awards sat in a different place on practices than on games. They now hold one place on every event, at both widths. Where attendance itself lives is deferred to the schedule deep dive (see Decisions).

          One visual difference from the mockup: the mockup drew a rule between the practice plan and the Awards section. The window stacks its sections without rules — a game’s score, tags and awards stack the same way — so the build matches the window, not the drawing.

          Review and QA (2026-09-25): /review at the high-risk tier, four lenses — no Critical, High or Medium findings; one advisory applied (the edit route re-checks that an award's event belongs to the team before reading its type). The owner marked the §235 walk complete. Committed on dev; no migration, so it ships with the next promote.

          Tests: the unlock rule, the label, the kind and both sentences across every event type (rep-award-occasion.test.ts); the door on a practice (coach-schedule-doors.test.ts); the wiring — route, window, placement, report, merge preview (coach-awards-any-event.test.ts); the phone guard’s pinned expression updated.
