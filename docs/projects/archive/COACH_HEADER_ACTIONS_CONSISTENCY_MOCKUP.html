Where the buttons live

What's there today

Forty screens sit under a team. Ten of them put an action in the page header. The rest either have no page-level action at all, or have one that's living somewhere in the body.

The decided shape

Every button sits with the thing it names. The header names Money, so it holds the hub's own doors — in and out. The tab bar names nothing a coach can act on, so it stays pure navigation. The tab's content names the budget, so that's where "Add Line" lives.

The budget table starts here.

Import and Export never change. They're the hub's own doors, identical on all seven tabs, so a coach learns them once and the header above the tab bar stops making a promise it can't keep. Add Line comes down into the budget itself, joining the List / By period control the tab already has — so it changes with the tab because it's inside the tab, and the tab bar goes back to being purely a way to move around. Nothing was added to the page: that row already existed.

Where a button goes: the nearest chrome that names what it acts on. On Roster, the page header says "Roster", so Add Player belongs there. In a hub the page header says "Money" — it names the container, not the thing — so a create button sitting up there is orphaned. The nearest chrome that names the budget is the budget's own toolbar. That's the whole rule, and it explains why standard pages pull their actions up into the header while hub tabs push their creates down into content: both are moving toward the label that describes them.

How we got here

Considered — actions on the tab row

Buttons ride the tab row. Set aside twice over: eight tabs plus buttons don't fit without shortening labels, and a navigation control is the wrong place to hang a verb.

Considered — a tightened band

Keeps full tab labels and closes the gaps, but costs a band of height and still floats the buttons closer to the content than to their tab.

Considered — a Data Tools destination

One page for all data in and out, as the tournament admin has. Set aside: it moves the button away from the moment of need and adds a destination to a nav we've been pruning.

The decided shape borrows the honesty of the third without its destination, and adds the dataset menus that let Import and Export sit above the tabs without lying — then sends the creates the other way, down to the content they act on.

Inside the menus

Each menu names the data, not the file type — the coach picks what, then which format, on one level. A row only appears where the coach has access to that data.

Why a menu fixes the lie. The objection to putting these buttons above the tab bar was that they'd look hub-wide while belonging to one tab. Making them dataset pickers makes them genuinely hub-wide — and it answers a question the current design can't: a coach who wants the season's money in a spreadsheet no longer has to guess which tab hides the export.

On a phone

Spreadsheets aren't a phone job. A coach isn't importing a budget on a sideline, and an exported .xlsx lands in a downloads folder they'll never open there. So the rule is about what the export produces, not which screen it's on.

OutputPhoneWhy
Import (any dataset) hidden A once-a-season setup act done from a spreadsheet the club already has. Nobody does it standing at a field.
Excel & CSV hidden Produces a file whose only use is on a computer.
PDF kept Something a coach reads, shows a parent, or forwards — a lineup card, a dues statement, a certificate.
Add to calendar kept The most phone-native thing in the portal: the schedule goes straight into the coach's own calendar.
One thing this retires, so it isn't lost quietly. The importers were built with a paste-a-block mode specifically because phones have no file picker. Hiding Import in the phone header makes that path unreachable. The fix costs nothing: the empty state keeps its import offer at every width. A coach who opens an empty budget on a phone is still offered a way in — it's only the persistent header button that goes.

Standard pages

Roster and Schedule are already closest to right and set the pattern. Single-dataset screens keep plain Import and Export buttons — a menu with one item in it is a worse button. Elsewhere it is not simply "move the stray buttons up": each one has to earn the header, and on the screen with the most of them, only one does.

The rules

Twelve rules, extending the 2026-08-11 header ruling rather than replacing it. Three of them exist because a render looked jumbled and the phone check hadn't been run yet.

  • Verbs only A page header holds things this page does. Not navigation to another page, not view switches, not status displays. Roster's "Attendance" moves out; Overview's setup ring is a display and gets a slot of its own.
  • One order Left to right: data in, data out, then the single primary. Help "?" stays outside the group in its own corner, untouched.
  • In and out travel together If a screen exports a table and the same rows can be created in bulk, both live in the header. Roster gains Import; three money datasets gain Export.
  • One name, one weight "Import payables" becomes "Import". Import and Export are always the same weight of button. Every page's main create action is the filled lime button, so "Add Line" and "Add Expense" stop being outlined while "New Fundraiser" is filled. "Add from a past season" keeps its own name — it's a different verb.
  • Nothing hides Header actions survive the empty state and every view mode. A coach shouldn't have to add one player, or switch back to List, to find the button.
  • Nearest label wins A button belongs to the nearest chrome that names what it acts on. A page header naming the page holds that page's actions. A hub header names the hub, so it holds only hub-wide things — everything a single tab does lives in that tab's own toolbar, joining whatever filter or view control the tab already has.
  • Hubs get menus A hub holding several datasets puts them behind Import ▾ / Export ▾ in the page header, constant across every tab. A single-dataset screen keeps a plain button — a one-item menu is a worse button. Tab bars stay pure navigation; no verbs hang off them.
  • One verb, one button Two ways to create the same thing is one button with a choice inside it, not two buttons competing. "New template" and "Add from a past season" both make a template; they become New template ▾. Same for Drills.
  • Two, then a menu Two buttons plus help is the working cap for a page header — three was too many the moment it was drawn. Anything beyond either folds into the primary as a choice, or goes down to the toolbar of the list it acts on.
  • Icons only for words already met A secondary may collapse to an icon on a phone only where a coach would have met its label on a wider screen — Import, Export, Attendance. A button that exists only as an icon is a guessing game; it goes to the list toolbar with its words on instead.
  • Context keeps its export An export whose content depends on a selection lives beside that selection, not in the header. Awards' "Print N certificates" prints the chosen award type, so it belongs with the type filter — and as a PDF it survives on a phone.
  • Phones get outputs, not files On a phone the header offers only exports a coach can read, show or send — PDF and add-to-calendar. Spreadsheet exports and all imports drop out. Empty states keep their import offer at every width, so the paste-a-block path built for phones survives.
Not reopened. Nothing here touches the four rules of 2026-08-11 — no subtitles, the masthead owns season and role, actions right of the title, one shared header component. The help "?" stays chrome, alone in its corner at every width. These rules say which buttons go in that actions slot, how they're drawn, and which survive a phone.
