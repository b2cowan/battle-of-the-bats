## Question(s) this answers
Does the built family side keep the build rules (notice verbatim, health line, upload route, health words never on a no-sign-in page, no email-only sign-up row)? Seven decisions taken in the build to rule on, and what the review of the code found.

## Finding — passes
- **The fixed notice is verbatim from drawing tab 5** (`lib/club-form-family-words.ts` `notice`; rendered by `FormNotice`, once above the first of the club's questions the page shows, never editable). "In the United States" is true of production (Supabase and its file storage, us-east-2). "Uses them for nothing else" is true: no answer reaches an email, a log, a push or a bell line (routes log codes only). The club's privacy link shows only when `privacy_policy_url` is set (`getOrgPrivacyPolicyHref`), opened in a new tab with `noopener`.
- **The health line** ("Only answer what {club} needs to keep {child} safe.") shows under every question marked health, per child by first name, for the sign-up's own questions by "your child" / "your children".
- **The upload route** (`form/files/route.ts`): the file's type is read from its bytes (PDF, JPEG, PNG, HEIC), never from the browser; the stored name is sanitised; the bucket is private and on the org-purge list; no IP address or user agent is stored anywhere (the rate limit is in memory); logs hold codes only; it refuses a draft or finished season and a question that is not a live file question of that season's form. The page says what it asks for before the file goes up (the notice sits above the first question).
- **Health words never leave the server for a no-sign-in page:** Your sign-up reads "Answered" for a health answer and a health file's name is blanked; the Change response is redacted the same way; validation messages name the question and the child's first name only. Session storage holds no health answer and no file (call C3, as ruled).
- **No "scanned", "virus-checked" or "we confirm they read it"** anywhere (a unit test pins it). Words say families are asked to open a document.
- **The guardian-email-only sign-up row rule (2026-11-20) is kept.** The register route makes the sign-up row only when there is an answer, tick or file to save. Your sign-up's Change and re-tick create the row on first need, so the review's fix prunes it again when a save fails, an empty save arrives, the last answer is cleared or the only tick is undone (`pruneEmptySubmission`; a unit test pins it). The mig 515 trigger still removes it when the last child is deleted.

## The seven decisions — rulings
- **(a) A health answer's words are never sent back to Your sign-up: right, keep it.** The page opens from an emailed link with no sign-in; "Answered", with Change replacing or clearing it, is the safe reading. **New hole, closed in code:** the redaction reads the question's *current* health mark, so un-marking a question would have put every family's old answer on that page. A club can no longer take the mark off a question people have answered (`readQuestionInput`: "People have answered it, so it stays marked as health. To ask it without that mark, archive it and add a new question."). Turning the mark ON is always allowed. Rejected: storing the mark on each answer (a schema change for a case the lock removes).
- **(b) The PDF hand-over receipt: acceptable, with a words rule for Part 3.** It proves our server served that version to that browser, once, within a day; it does not prove a person looked at it (a prefetch or a bot would earn one). The tick is the family's own statement. Part 3 must not render the hand-over as "read" or "viewed"; "link opened {time}" is the strongest honest phrase. Nothing is stored before the sign-up. Failing closed with no secret is right.
- **(c) Files stored "waiting" before the sign-up: acceptable only with the sweep actually scheduled.** This is the one place the build holds health information with no registration behind it (Part 1's review said "never a server-side draft"; ruling 9 chose waiting files, with deletion within a day). Until mig 516 runs, the sweep happens only when someone uploads a file (a few of the oldest, on any club), so on a quiet platform a health document can sit for days. **Rule: mig 516 (the 6-hourly schedule) is a release condition for promoting Parts 1–3, and no policy sentence says "within a day" until it is live** (same rule as the §9 retention sentence). A replaced file whose storage delete fails stays in storage until the club's purge: it has a `removed` row, no longer reaches the club or the family, and is carried to Part 3 with the stored files of a deleted registration (same cause: the object outlives its row). Part 3 must close both before promotion.
- **(d) The consent ledger names a PDF by file name + version: right.** The club's own document name and the version number; nothing about the family. The ticks table is the evidence.
- **(e) A document added after the family signed up shows "{club} added it on {date}" on Your sign-up: acceptable.** It is a plain statement of fact and asks for one tick, "places aren't affected" is said. The tick records only the guardian's email and the time (no IP, ruling kept), so a second parent holding the link can tick for the family; that is the same proof the page already relies on (ruling 20). Undo is possible only with the tick ids returned by a re-tick made in the last two minutes, so a placement tick cannot be undone from the page.
- **(f) Change silently overwrites or clears a health answer for anyone holding the link: keep it, add one thing at Part 3.** No soft-delete or history of the old words: keeping a cleared health answer to protect it is the opposite of data minimisation, and the family (the person the data is about) is entitled to correct it. The safety risk is the club not knowing a safety answer changed. **Part 3 rule:** the club's record shows "Answer changed by the family {date}" on a health answer whose `updated_at` is later than the sign-up (and "Answer cleared by the family {date}" is not possible without a history, so Part 3 shows "Not answered" plus the changed date). No notification email (every emailed health reference is barred).
- **(g) The child's free-text Additional notes were kept in the tab's storage on reload and often hold an allergy: fixed.** Notes are now never kept, and the reload note says so ("Additional notes aren't kept if the page reloads. Please enter them again.", combined with the health and file sentences when more than one applies). Cost: re-typing a short note after a reload.

## What the review of the code also changed (words and code in Part 2 files)
- The upload route refuses a body far over the limit before reading it; the hand-over cookie is always marked Secure in production; a failed storage delete logs a code, not a message (a message can echo a file name such as an allergy note).
- A file deleted while a sign-up was claiming it can no longer remove the stored copy of a file that sign-up attached (the sweep, Remove and the question delete now delete the row first, then the stored file).

## For the owner
- **C5 (schedule, mig 516): yes.** Make it a release condition; the sweep is the only thing that makes "within a day" true.
- **C7 (health answers hidden on Your sign-up): keep it**, with the lock above. The cost is that a family with a health answer sees "Answered" and cannot read it back; Change replaces it.
- The hosting facts are unchanged: production is us-east-2; the dev project is ca-central-1 and the notice describes production.
