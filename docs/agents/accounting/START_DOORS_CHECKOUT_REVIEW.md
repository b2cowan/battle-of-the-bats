## Question(s) this answers
On-sale pages S2: new public doors `/start/club` and `/start/league` make an organization on the free Tournament plan (no Founding comp), remember the intended plan (`organizations.start_plan`, mig 508), and send its owner through a plan step, a billing address and the existing Stripe checkout with a 90 / 90 / 30-day trial.

## Finding

**1. Nothing about what is charged, collected, invoiced, recorded or reported changes.** The Stripe session is built from the same code path as before: same `mode: 'subscription'`, same `...TAXED_CHECKOUT` (automatic tax, tax-ID collection, `customer_update.name: 'auto'`), same `line_items`, same `subscription_data.metadata` and session `metadata` (`orgId, planKey, billingCycle, buyer user, comeback flag`), same customer (`ensureStripeCustomer`, one customer per organization). The only diffs are (a) `success_url` / `cancel_url` (door returns; the door's success URL drops `success=1` for Stripe's session-id placeholder), (b) the trial expression, now `trialDaysAfterHistory(configured, returning)`, which is byte-for-byte the old `configured > 0 && !returning ? configured : 0`, and (c) a 503 refusal before any Stripe call. The webhook, the charge tax records and the Sales by month read are all keyed on Stripe invoice events and the metadata above, not on the return URL or the door, so a buyer who closes the tab before the return page is still recorded. The 503 is correctly placed (after the Terms check, before the billing-address check and before any customer is created), so "Nothing has been charged" is true. It is scoped to the three new plans on a live key, so it does not stop Tournament Plus or the Coaches Portal.

**2. The plan step's money words.**
- Price + "plus applicable taxes" (`BILLING_TAX_WORDS.plusTax`) under each price, and again in the billing-address sub-line: correct and consistent with the rest of the product (T4 rule).
- `planTrialLine`: "{N}-day trial — you add a payment method at checkout, and you're first charged, plus applicable taxes, when the trial ends." Correct. The tax is inside the sentence, which is the right place: no tax exists until that first charge. It does not say "free" and does not promise an amount.
- **"The full charge is due today at checkout." (`clubUpgrade.noTrial`): one word short.** It is true that the charge is due now, but it sits on a card whose only figure is the pre-tax price, and Stripe will add GST/HST on top. "The full charge" reads as "the figure on this card". Fix (exact words below): put the tax inside it, as `planTrialLine` does. The string is shared with the Premium → Club move window (`PlanMoveDialog.tsx:380`), which prints a quote with the tax lines next to it; adding the clause there is harmless and keeps ONE sentence (the project's own rule for trial sentences). Reach: at the doors this line shows only for an organization that held a subscription before and fell back to the free Tournament plan with `start_plan` still set (a brand-new door organization has no Stripe customer, so no history), so it is a low-frequency line.
- **$0 trial invoice.** Stripe makes a $0 invoice when a subscription starts with a trial. No consideration is paid for a free trial period, so no GST/HST is collectible on it, and `charge-tax-record.ts:35` already treats a Canadian line "rated at $0 on a $0 trial" as rated (not "missing"). Nothing to change; it is the same path the Club, Tournament Plus and Coaches Portal trials already take, now used more often.
- **Annual first charge at trial end.** Tax point = the invoice date (`GST_HST_RETURN_LINES.md`), which is the trial-end day, so the sale and its tax fall in whichever return period the trial ends in (90 days after sign-up for Club). Place of supply and the rate come from the customer's billing address on that day, not the sign-up day: if the club corrects its province during the trial, the rate follows. For a yearly Club · Association the first charge is $3,790 before tax, an invoice over $500, so the "recipient's name" rule applies (`GST_HST_ON_SUBSCRIPTIONS_CANADA.md`, the $500 name rule); the name on the invoice is `org.name`, the club name the owner typed at step 2, which satisfies it (it is the name the buyer gave). The sentence "plus applicable taxes" does not show the dollar tax before the buyer commits; that is Stripe's page, see the walk item below.

**3. An address saved before checkout, Québec refused at checkout, US refused on prod: no tax-record consequence.** Order of events for a Québec address: the plan step saves it with `PUT /api/billing/location` (no region check on a plain save), then `create-checkout` runs `requireBillingLocation(..., { purchase: true })`, which refuses a Québec address with `billing_region_closed` BEFORE `ensureStripeCustomer`. So an abandoned door organization with a Québec address has: no Stripe customer, no subscription, no invoice, no row in `platform_charge_tax_records`, and stays free Tournament. Tax records and Sales by month are built only from Stripe invoices, so they never see it. There is no GST/HST or QST exposure (nothing sold). If Québec later opens, the saved address already places the buyer correctly. The same pattern already existed for Run a tournament's plan step; the doors do not add a new one. US is the same shape (US sales closed on prod: no button, and checkout refuses). The one housekeeping point, which is not accounting: an abandoned door organization that never reaches checkout lingers with a stored address (privacy retention, for `/legal`/`/dba`, not for the books).

**4. A second trial needs a second email, and that is not an accounting concern.** Trial history is per Stripe customer (`hadSubscriptionBefore(customerId)`), and the customer is per organization. The one-organization-per-person rule is the only thing tying two trials to one person, so a second email is a second organization and a second trial. Accounting effect: a $0 invoice per trial, then, if the card is charged at the end, an ordinary taxable sale; if the card then fails, the unpaid invoice is the existing case in `UNPAID_SUBSCRIPTION_INVOICES.md` (GST/HST owed on issue, recoverable on line 107 once written off). A card on file before the trial starts (which these doors require) is what keeps that small. The cost of a serial trial-taker is in growth/abuse, not the return.

**5. Bookkeeping.** Door purchases flow in the same as every other checkout. No webhook, bookkeeping, charge-tax-record or sales-report file is touched by this change (`git status`), and the metadata that those read (`orgId`, `planKey`, `billingCycle`) is unchanged. The new plan keys are not new to the books: the kind and position (taxed / zero-rated / missing) are decided from the invoice's tax lines and the buyer's address, not from the plan key. What I could not prove from code: that Stripe's checkout page shows the buyer the tax on the after-trial charge. See the walk item.

## Recommendation
See the numbered verdicts in the report that came with this record; in short: one wording fix (tax into the no-second-trial sentence), one walk item on Stripe's page, one pre-flip reminder (live Canada tax registration), two things recorded and nothing else.
